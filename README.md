# BuiltWright

Industrial trades education and troubleshooting: a static, offline-capable web app
covering 21 content modules, a symptom-first diagnostic hub, full-text search, a PM
task library, reference tables, a root cause report form, and printable pocket cards.

No build step and no dependencies. Every page is standalone HTML with inline CSS and
JS, linked by URL hashes, and the set installs as a PWA over https.

## Layout

```
app/     the application. All files live in one flat folder because sw.js,
         manifest.json and every internal link are folder-relative.
  data/    the modules extracted as JSON, served with the app
  bw.css   the stylesheet shared by every content module
  bw-renderer.js, module.html   the renderer and its page
build/   extract.mjs, validate.mjs and parity.mjs, plus the Python scripts
         the current files were generated by and pt_styles.html, the
         canonical head and CSS block.
docs/    CLAUDE_CODE_BRIEF.md (architecture and migration plan) and
         README_hosting.txt (hosting, offline, print).
```

## Running it

Open `app/builtwright_diagnose_hub_v1.html` directly in a browser, or serve the
folder:

```sh
python3 -m http.server -d app 8000
```

Then visit http://localhost:8000/builtwright_diagnose_hub_v1.html

Service workers need https or localhost, so opening the files over `file://` or plain
http works but does not cache for offline use.

## Deploying

Copy the contents of `app/` to the root of any static host (Netlify, Cloudflare Pages,
a plant intranet server). For GitHub Pages, publish `app/` through a Pages workflow, or
serve the repository root and move the files up, since Pages only builds from the root
or from `/docs`.

To ship an update, bump the `CACHE` version in `sw.js` so installed phones fetch the
new files.

## Local data

PM task ticks and intervals and the root cause report form use `localStorage`. Nothing
leaves the device.

## Build scripts

`build/` holds the generators and audit passes described in the brief: `build_tools.py`
(extracts prevent tails into the PM library, rebuilds the search index, adds print CSS
and PWA tags, regenerates `sw.js`, runs link and onclick integrity checks),
`add_selfcheck.py` with `qbank*.py`, and the `review_pass.py`, `older_modules_parity.py`
and `pass3.py` enrichment passes.

They are committed as they ran, so they still carry the absolute paths of the sandbox
they were written in (`/mnt/user-data/outputs/` for the app folder and
`/home/claude/pt_styles.html` for the style block). Point those at `app/` and
`build/pt_styles.html` before running them here.

## The data layer

`build/extract.mjs` reads `app/` and writes `data/`, which is step one of the migration
in the brief: get the content out of the HTML so a renderer can be built against it.

```sh
node build/extract.mjs    # app/ -> data/
node build/validate.mjs   # structural checks, exits non-zero on failure
```

```
app/data/modules/<key>.json   one per module: tabs, cards, diagnostic trees,
                              self-check bank, each panel as an HTML fragment,
                              the module's own CSS, and the render config
app/data/hub.json             the hub module registry, node tree and symptom list
app/data/pm.json              PM task library tasks, components and intervals
app/data/search.json          the prebuilt search index and ranking table
app/data/extract-report.json  per module counts and anything the extractor skipped
```

The extractor evaluates each data literal in an isolated VM rather than pattern matching
the source, so multi-line formatting and braces inside prose do not throw the counts off.
Anything that is not a pure literal, and the handful of variables that hold runtime click
state, are recorded in the skip list in `extract-report.json` instead of being guessed at.

`app/data/` is committed so the JSON can be diffed when the HTML changes, and it sits
inside `app/` so it is served with the application rather than needing a separate copy.

## The renderer

`app/bw-renderer.js` is one plain script, no build step and no dependencies, that renders
a module from its JSON: the tab bar, the card groups, the diagnostic tree and the
self-check. `app/module.html?m=<key>` is the page that mounts it.

```sh
python3 -m http.server -d app 8765
# http://localhost:8765/module.html?m=fans
```

Every content module used to carry its own copy of the same nine functions. They are now
one implementation each. The copies were already near identical: `card`, `scRender`,
`scAnswer` and `scReset` were byte for byte the same in all 20 modules, and the 20
"different" `renderDiag` functions turned out to be the same function with different
element ids. The renderer takes those ids, the tab that starts the tree, and each card
group's wiring from a config that `build/extract.mjs` reads back out of the modules
themselves, so nothing is hand maintained.

Panel fragments are injected as they are, which is why their inline handlers keep
working: `mount()` installs the module's own function names (`selectType`,
`selectBearing` and so on) from that config.

`app/bw.css` holds the 86 CSS blocks every content module shares; each module's JSON
carries only what it adds on top. The two together are exactly the rule set the module
had inline, which `build/validate.mjs` checks.

## Validation

`node build/validate.mjs` checks, over `data/` and `app/`:

- every `next:` in a diagnostic tree resolves to a node (570 transitions)
- every result node has a `cls` of action, fix, escalate or info, plus a label and text
- every result carries a prevent-recurrence tail, which is what the PM library is built from
- every self-check entry is a stem, at least two options, an in-range answer index and an explanation
- every tab has a matching panel in its HTML file and an extracted fragment
- any module with a Safety tab has it last
- every `href` resolves to a file and, where a fragment is used, to a panel id
- `node --check` on every inline `<script>` block
- zero em dashes
- the totals in `builtwright_index.json` match what was extracted

- the body of every page balances, and all panels sit at the same depth
- `bw.css` plus a module's own blocks are exactly the rule set it had inline

Current state: 23 modules, 380 diagnostic results, 570 transitions, 423 self-check
questions, 162 links, 52 script blocks, all passing.

## Parity

`build/parity.mjs` is the acceptance test the brief asks for. With a server running on
`app/`, it loads each content module twice, once as the original page and once through
the renderer, switches to every tab on both, walks the diagnostic tree three steps and
answers a self-check question, then compares the rendered text, a census of every element
and a screenshot of each panel.

```sh
python3 -m http.server -d app 8765 &
node build/parity.mjs           # all content modules, or pass keys to narrow it
```

Current state: 20 modules, 216 comparisons identical, 176 screenshot pairs all matching
in size. Screenshots land in `.parity/` for eyeballing.
