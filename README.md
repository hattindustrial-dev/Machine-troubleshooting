# BuiltWright

Industrial trades education and troubleshooting: a static, offline-capable web app
covering 21 content modules, a symptom-first diagnostic hub, full-text search, a PM
task library, reference tables, a root cause report form, and printable pocket cards.

No build step and no dependencies. Every page is standalone HTML with inline CSS and
JS, linked by URL hashes, and the set installs as a PWA over https.

## Layout

```
app/     the application. All files live in one flat folder because sw.js,
         manifest.json and every internal link are folder-relative.
build/   the Python scripts the current files were generated by, plus
         pt_styles.html, the canonical head and CSS block.
docs/    CLAUDE_CODE_BRIEF.md (architecture and migration plan) and
         README_hosting.txt (hosting, offline, print).
```

## Running it

Open `app/builtwright_diagnose_hub_v1.html` directly in a browser, or serve the
folder:

```sh
python3 -m http.server -d app 8000
```

Then visit http://localhost:8000/builtwright_diagnose_hub_v1.html

Service workers need https or localhost, so opening the files over `file://` or plain
http works but does not cache for offline use.

## Deploying

Copy the contents of `app/` to the root of any static host (Netlify, Cloudflare Pages,
a plant intranet server). For GitHub Pages, publish `app/` through a Pages workflow, or
serve the repository root and move the files up, since Pages only builds from the root
or from `/docs`.

To ship an update, bump the `CACHE` version in `sw.js` so installed phones fetch the
new files.

## Local data

PM task ticks and intervals and the root cause report form use `localStorage`. Nothing
leaves the device.

## Build scripts

`build/` holds the generators and audit passes described in the brief: `build_tools.py`
(extracts prevent tails into the PM library, rebuilds the search index, adds print CSS
and PWA tags, regenerates `sw.js`, runs link and onclick integrity checks),
`add_selfcheck.py` with `qbank*.py`, and the `review_pass.py`, `older_modules_parity.py`
and `pass3.py` enrichment passes.

They are committed as they ran, so they still carry the absolute paths of the sandbox
they were written in (`/mnt/user-data/outputs/` for the app folder and
`/home/claude/pt_styles.html` for the style block). Point those at `app/` and
`build/pt_styles.html` before running them here.

## Validation

Checks that must keep passing after any content change:

- `node --check` on every inline `<script>` block (52 blocks)
- every `next:` in a `diagNodes` tree resolves to a node (570 references)
- every `href` resolves to a file and, where a fragment is used, to a panel id
- hub registry tabs exist on the module they point to
- zero em dashes

The committed snapshot passes all of these.

## House conventions

Design tokens, panel and tab structure, diagnostic tree and self-check shapes, and the
writing style rules are documented in `docs/CLAUDE_CODE_BRIEF.md`. Plant-specific
numbers belong in the planned facility layer, never in the universal modules.
